# SEO content audit for Rutas Mallabia

Before anything else: this repo has a `CLAUDE.md` at its root with the standing rules for the whole site, and this skill does not override or replace a single one of them — it operates inside them. Re-read `CLAUDE.md` if it's not already fresh in context. The two that matter most for SEO work specifically, because they're the ones an "optimization" mindset most easily tramples:

1. **Never invent a route fact to make a sentence sound better.** Distance, elevation, place names, water sources — all come from the real GPX or from the user. An SEO description that says "sube hasta los 700m" because that sounds punchier than the real 655m is a factual error on a site whose whole premise is that the data is real. If a number in the JSON-LD or the description doesn't match the `.facts` block, that's a bug to report and fix by looking at the real number — never by picking whichever number reads better.
2. **Never touch the user's narrative prose** (the `<div class="body-copy">` paragraphs) without being asked. He's said this explicitly and repeatedly: he writes those himself, in his own voice, and a "SEO improvement" that quietly rewords his account of a climb is not welcome. Everything in this skill lives in the metadata layer around that prose, not inside it.

The rest of `CLAUDE.md` still applies in full while doing this: the Spanish source is the only thing hand-edited (Basque is generated by `make_eu.py` from `eu.py`, never touched directly); `make_eu.py` and `build.py` run after every change and both must come back clean; always say out loud when you notice a missing or wrong fact even if nobody asked; and — the one that trips people up most in a "just polish the metadata" task — a small metadata edit is still exactly the kind of change that needs `git status` checked and a real commit, same as any other content change on this site. "It's just SEO" is not a reason to skip the verification loop.

This site already has a real SEO scaffold on every page — title, meta description, Open Graph, hreflang, JSON-LD. The job here is almost never "add SEO from scratch." It's auditing whether a specific page's scaffold is actually doing its job, and fixing it without breaking the rules above.

## What you're allowed to touch, and what you're not

**Free to optimize** (this is the actual job):
- `<title>`, `<meta name="description">`, `og:title`, `og:description`, `og:image`
- JSON-LD `BreadcrumbList` and `TouristTrip` blocks
- `<link rel="canonical">` and the `hreflang` alternates
- Image `alt` text
- Heading structure (`<h1>`, the eyebrow line above it)
- The `full-name` subtitle paragraph (a structural/descriptive field, not narrative — see the `argineta` fix in git history where "por Osma" was corrected to "por Elgeta" because the route doesn't actually pass through Osma)

**Off-limits without explicit permission**:
- Any `<p>` inside `.body-copy` — the route's told-in-his-own-voice narrative
- The `.parada` "para quién es" paragraph
- Anything in `_tail.eu.html` / `_head.eu.html` directly — these are generated by `make_eu.py` from `src/i18n/eu.py`. Edit the Spanish source and the matching `eu.py` entry, then regenerate. Editing the `.eu.html` file by hand gets silently overwritten on the next build and is exactly the kind of mistake that erases work.
- `sitemap.xml`, the "Rutas parecidas" internal links — both are auto-generated by `build.py` from distance/elevation similarity; don't hand-edit them.

If an audit finding would require touching narrative prose or a real fact (e.g. "this paragraph never mentions Mallabia by name" or "the elevation gain here looks wrong"), report it and ask — don't fix it silently. That's not a formality here; it's the same rule that already caught real bugs this session (a wrong "por Osma" subtitle, a duplicated card photo, an untranslated footer link). Flagging is how those get caught before they ship, not after.

## Audit checklist

Work through a page's `src/<slug>_head.html` and `_tail.html` (the Spanish source — the `.eu.html` pair is downstream and regenerates automatically once these and `eu.py` are right).

### 1. Title tag
- Format already established: `<Name of route> · Ruta de <BTT/senderismo/senderismo y BTT> — Rutas Mallabia`. Match it — a page whose title doesn't follow the pattern stands out as broken, not distinctive.
- Length: aim for 50–60 characters before the fixed `— Rutas Mallabia` suffix. Longer gets truncated in search results.
- Must be unique across all 49 pages. Check with:
  ```
  grep -h '<title>' src/*_head.html | sort | uniq -d
  ```
  Any line that comes back is a real collision to fix, not a style nit.

### 2. Meta description
- `<meta name="description">` and the matching `og:description` (they're usually identical on this site — keep them that way unless there's a real reason to diverge).
- Length: 120–155 characters. Under 120 wastes space Google would otherwise fill with a snippet from the page; over ~155 gets cut off with an ellipsis mid-word, which reads as sloppy.
- Must describe *this* page specifically — real distance, real terrain, the actual landmarks it passes, not a generic "ruta bonita cerca de Mallabia" that could sit on any of the 49 pages. Pull the specifics from the `.facts` block and the first paragraph of `body-copy`, don't write new ones.
- Check for duplicates the same way as the title:
  ```
  grep -h 'meta name="description"' src/*_head.html | sort | uniq -d
  ```

### 3. Open Graph / social preview
- `og:image` must point at a real file that exists in `img/` — a broken og:image means the page looks blank when shared on WhatsApp/Twitter, which is how most of this site's traffic actually gets shared.
- `og:title` sometimes needs its own `<meta property="og:title">` distinct from `<title>` if the page has a custom social-share title (check `mallabia_head.html` for the one exception — the home page). For a route page, mirroring `<title>` is correct; don't invent a different one.

### 4. Canonical + hreflang
- Every page needs `<link rel="canonical">` pointing at its own `https://trabakutik.com/<slug>.html`, and three `hreflang` alternates: `es`, `eu`, `x-default` (both pointing at the `.html` for x-default/es, `.eu.html` for eu).
- These get generated correctly by `build.py` as long as the page is registered in `PAGES` — if you're auditing a page that's missing one of these, the bug is almost certainly that it's missing from `PAGES` in `build.py` or `PAGES`/`ROUTE_PAGES` in `make_eu.py`, not something to patch by hand in the built HTML.

### 5. JSON-LD structured data
Two blocks: `BreadcrumbList` and `TouristTrip`. For `TouristTrip`, cross-check every number against the page's own `.facts` block — they should be the *same* number, not independently-sourced:
```
grep -A3 '"@type": "TouristTrip"' src/<slug>_head.html
grep 'class="fact"' src/<slug>_tail.html
```
A mismatch here (e.g. JSON-LD says 850m of desnivel, the fact tile says 900m) is a real bug — since Google reads the JSON-LD, a stale number there actively misleads search results even after the visible page was corrected. When you find one, the fix is to match whichever number is the current, GPX-derived one — check the `facts-note` disclaimer and the actual GPX if genuinely unsure which is current, never split the difference.

### 6. Image alt text
- Every `<img>` needs an `alt` that's specific and accurate — "Sarcófagos bajo los robles de la Necrópolis de Argiñeta, con la ermita al fondo" is doing real work; "Foto de la ruta" is not.
- Never upgrade an alt's accuracy by guessing what's in the photo. If you haven't seen the image and the user hasn't described it, say the alt is generic and ask, rather than writing a more specific-sounding one that might be wrong.
- Don't keyword-stuff alts with "Mallabia BTT ruta senderismo" repeated across every image on the page — it reads as spam to both users and search engines, and this site's actual descriptive alts already outperform that pattern.
- Check the lightbox's own generic alt too (`id="lightboxImg"` in the hero) — it should name the actual route, not just say "Foto ampliada del recorrido".

### 7. Headings and internal links
- One `<h1>` per page (the route name), matching the `<title>`'s theme — don't introduce a second h1.
- Cross-references to other routes in body-copy (e.g. "el mismo pico de la ruta de <a href="arietzu.html">Osmagain y Arietzu</a>") are good for SEO *and* already the site's convention — but this is body-copy, so adding one is still a content decision for the user, not something to insert unprompted.
- The "Rutas parecidas" block at the bottom is auto-generated by `build.py` from distance/elevation similarity — verify it looks sane after a build, don't hand-edit it.

## Workflow

1. **Read** the target page's `_head.html` and `_tail.html` (Spanish source only).
2. **Run the checklist above.** For each item, note whether it passes, and if not, what the actual problem is (too long / too short / duplicate / mismatched number / missing / generic) — vague "could be better" isn't a finding.
3. **Present findings before editing anything** — this is an audit first. Say what's wrong and what you'd change it to, especially for anything touching a number or a place name, since those need the same real-source verification as any other route fact on this site (GPX, or the user directly).
4. Once approved, edit:
   - The ES source (`_head.html`/`_tail.html`)
   - The matching `src/i18n/eu.py` entry for anything that changed (title/description dicts, or the page's own per-page dict for other strings) — search for the *old* text first so you replace the exact key, not a near-miss.
5. Regenerate and verify, same as any other content change on this site:
   ```
   python3 src/i18n/make_eu.py   # must run clean — no SystemExit, no SPANISH_TELLS hits
   python3 src/build.py
   ```
   Then grep the built `.html` and `.eu.html` to confirm the change landed in both languages, and re-check the duplicate-title/description greps above still come back clean site-wide (a fix on one page can't create a new collision with another).
6. `git status` before committing — this workflow only touches a couple of files per page; if more show up, figure out why before staging.

## What "good" looks like here

The bar isn't "more keywords." It's a title and description that would make someone searching "ruta btt Mallabia Duranguesado" actually click this result over a generic Wikiloc listing, made of real, specific, verifiable details about this one route — the same standard the rest of the site already holds itself to for the visible content. If an SEO change and a factual-accuracy change would ever conflict, factual accuracy wins without exception.
